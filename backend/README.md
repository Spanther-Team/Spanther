# Бэкенд SPANTHER

Схема базы для аккаунтов, профилей игроков, итогов игр и премиума, и вход по почте и паролю. Вход в приложении необязателен: без него игроки и их калибровка живут на телефоне, как раньше. Взрослый, который вошёл, видит своих игроков и их прогресс на всех своих телефонах. Архитектура описана в документе «SPANTHER: профили, калибровка и бэкенд».

Приложение ходит в Supabase напрямую по HTTP (`GazeCore/Sources/GazeCore/Backend.swift`, без SDK): вход через Supabase Auth, таблицы через его REST API. В приложении лежат только адрес проекта и публичный ключ (`SpantherGaze/App/BackendSettings.swift`); пока они пустые, приложение не показывает вход вовсе.

## Что здесь лежит

| Файл | Что это |
|---|---|
| `supabase/migrations/20261126200000_profiles.sql` | таблицы, правила доступа к строкам, функции админа |
| `supabase/migrations/20261127090000_sign_in.sql` | почта у аккаунта, удаление аккаунта из приложения (`delete_my_account`) |
| `supabase/templates/confirmation.html`, `recovery.html` | письма с кодом: подтверждение почты и новый пароль, на языке, выбранном в приложении |
| `test/run.sh` | проверка схемы на временном Postgres в Docker |
| `test/e2e.sh` | вся цепочка приложения на настоящих Supabase Auth и PostgREST в Docker, с почтовым ящиком для писем |

## Таблицы

| Таблица | Что в ней | Кто видит и меняет |
|---|---|---|
| `accounts` | один взрослый: копия почты входа, язык, роль (user или admin), премиум до даты | владелец читает свою строку и меняет только язык; роль и премиум меняет админ |
| `profiles` | игроки: тот же id, что на телефоне, имя, цвет, год рождения, прогресс, время изменения и удаления | только владелец аккаунта |
| `plays` | итог одной игры: игрок, режим, сложность, начало, длительность, очки, точность, попадания, промахи, сборка | владелец добавляет и читает, изменить и удалить нельзя |
| `admin_log` | каждое изменение премиума и роли: кто, кому, когда, было и стало | только админ |

Без входа (публичный ключ без токена) база не отдаёт ничего.

## Как база сверяет два телефона

* Время изменения ставит телефон, а метку для забора новых строк (`server_updated_at`) ставит сервер, поэтому неверные часы на телефоне не теряют изменения.
* Имя, цвет и год рождения: побеждает более позднее изменение. Старая запись с телефона, который был без сети, ничего не откатывает.
* Прогресс: ключи с обеих сторон остаются, при споре по одному ключу побеждает более позднее значение. Открытый уровень не закрывается обратно. Ключ прогресса синхронизация не удаляет.
* Удалённый игрок остаётся удалённым (пометка `deleted_at`), строки игроков приложение не стирает.
* Запись без изменений пропускается, чтобы другие телефоны не забирали её снова.
* Игры только добавляются: повторная отправка той же игры (тот же id) ничего не дублирует.

## Что никогда не попадает в базу

Видео с камеры, калибровка и модель взгляда игрока, CSV сессий, дети клиники и их замеры. Всё это остаётся на телефоне.

## Вход

* Регистрация: почта и пароль не короче 8 знаков, затем 6 цифр из письма. Код вместо ссылки: ссылка из письма открыла бы браузер, а код вводится прямо в приложении.
* Забытый пароль: код из письма и новый пароль. После нового пароля другие телефоны этого аккаунта просят войти заново.
* Выход и «Удалить аккаунт» в листе «Игроки», как требует App Store (правило 5.1.1). Удаление сразу стирает аккаунт, его игроков и итоги игр на сервере; игроки на этом телефоне остаются.
* Сессия хранится в Keychain телефона. После переустановки приложения вход начинается заново.

## Как приложение сверяется с аккаунтом

* При входе, при каждом изменении игроков (через 2 секунды), после каждой игры и при возвращении в приложение.
* Сначала забирает всех игроков аккаунта, сливает их со своими по правилам выше, затем отправляет то, чего в аккаунте нет, затем итоги игр, которые ждут на телефоне.
* Первый игрок нового телефона, у которого нет ни имени, ни прогресса, ни игр, уступает место игрокам аккаунта, чтобы в аккаунте не копились «Игрок 1».
* Вошёл другой взрослый: игроки прежнего аккаунта уходят с телефона (они остаются в своём аккаунте и вернутся с ним), игроки, созданные без входа, переходят в новый аккаунт.
* Итоги игр детей клиники и игр бота не отправляются никогда.

## Как поставить на Supabase

1. Создать проект на supabase.com, регион Central EU (Frankfurt). Пароль базы сохранить у себя и никому не отправлять. До первых настоящих пользователей та же схема переезжает на свой сервер в Казахстане.
2. SQL Editor: вставить `20261126200000_profiles.sql` целиком и нажать Run, затем так же `20261127090000_sign_in.sql`. Или из папки `backend`: `supabase link` и `supabase db push`.
3. Authentication, вход по почте (Email provider): включён, Confirm email включён, минимальная длина пароля 8, длина кода (Email OTP Length) 6, срок кода 3600 секунд.
4. Authentication, шаблоны писем (Email Templates): в Confirm signup вставить `templates/confirmation.html`, в Reset Password вставить `templates/recovery.html`. Тема обоих писем: `SPANTHER: код`.
5. Почта. Встроенная почта Supabase шлёт письма только адресам участников проекта (team) и всего несколько в час: для проверки регистрируйтесь со своей почты. Перед настоящими пользователями подключить свой SMTP (Authentication, SMTP Settings: Resend, Brevo или почта домена) с отправителем вроде `noreply@spanther.kz`.
6. Project Settings, API: прислать в чат только Project URL и публичный ключ (anon или publishable). Ключ `service_role` (secret) и пароль базы не присылать никому и не класть в приложение или в репозиторий.

## Админ

Админом становится аккаунт взрослого, а не игрок. Админов может быть несколько. Первый назначается один раз в SQL Editor, после того как он зарегистрировался в приложении:

```sql
update public.accounts set role = 'admin' where email = 'почта админа';
```

Дальше премиум включается вручную в панели Supabase (Table Editor или SQL Editor), а когда появится своя админка, функцией `set_premium`. В обоих случаях изменение попадает в `admin_log`.

```sql
update public.accounts set premium_until = '2027-12-31' where email = 'почта человека';
```

## Проверка

```sh
backend/test/run.sh
backend/test/e2e.sh
```

Скрипт поднимает Postgres 16 в Docker, создаёт то, что Supabase даёт каждому проекту (роли, `auth.users`, `auth.uid()`), ставит миграцию и проверяет: чужие игроки и игры не видны и не меняются, старая запись не откатывает новую, открытый уровень не закрывается, игра не дублируется и не меняется, пользователь не может дать себе премиум или роль админа, каждое изменение премиума и роли пишется в журнал, удаление аккаунта уносит его игроков и игры, удалить можно только свой аккаунт.

`e2e.sh` поднимает рядом настоящие Supabase Auth (GoTrue), PostgREST и почтовый ящик Mailpit, ставит обе миграции и шаблоны писем и проходит путь приложения кодом из GazeCore (`BackendCheck`): регистрация с кодом из письма на казахском и английском, неверный код, вход до подтверждения, занятая почта, короткий пароль, два телефона одного аккаунта сходятся на одних игроках, чужой игрок отклоняется, сброс пароля кодом, обновление и отзыв сессии, повторная отправка кода не чаще раза в минуту, удаление аккаунта. С `EXPIRY_WAIT=40` ещё ждёт, пока истекут токены, и проверяет их обновление.
