# Бэкенд SPANTHER

Схема базы для аккаунтов, профилей игроков, итогов игр и премиума. Приложение пока работает без неё: игроки и их калибровка живут на телефоне. Вход и синхронизация появятся на втором этапе, архитектура описана в документе «SPANTHER: профили, калибровка и бэкенд».

## Что здесь лежит

| Файл | Что это |
|---|---|
| `supabase/migrations/20261126200000_profiles.sql` | таблицы, правила доступа к строкам, функции админа |
| `supabase/functions/delete-account/index.ts` | удаление аккаунта из приложения (набросок, ещё не развёрнут) |
| `test/run.sh` | проверка схемы на временном Postgres в Docker |

## Таблицы

| Таблица | Что в ней | Кто видит и меняет |
|---|---|---|
| `accounts` | один взрослый: язык, роль (user или admin), премиум до даты | владелец читает свою строку и меняет только язык; роль и премиум меняет админ |
| `profiles` | игроки: тот же id, что на телефоне, имя, цвет, год рождения, прогресс, время изменения и удаления | только владелец аккаунта |
| `plays` | итог одной игры: игрок, режим, сложность, начало, длительность, очки, точность, попадания, промахи, сборка | владелец добавляет и читает, изменить и удалить нельзя |
| `admin_log` | каждое изменение премиума и роли: кто, кому, когда, было и стало | только админ |

Без входа (публичный ключ без токена) база не отдаёт ничего.

## Как база сверяет два телефона

* Время изменения ставит телефон, а метку для забора новых строк (`server_updated_at`) ставит сервер, поэтому неверные часы на телефоне не теряют изменения.
* Имя, цвет и год рождения: побеждает более позднее изменение. Старая запись с телефона, который был без сети, ничего не откатывает.
* Прогресс: ключи с обеих сторон остаются, при споре по одному ключу побеждает более позднее значение. Открытый уровень не закрывается обратно. Ключ прогресса синхронизация не удаляет.
* Удалённый игрок остаётся удалённым (пометка `deleted_at`), строки игроков приложение не стирает.
* Запись без изменений пропускается, чтобы другие телефоны не забирали её снова.
* Игры только добавляются: повторная отправка той же игры (тот же id) ничего не дублирует.

## Что никогда не попадает в базу

Видео с камеры, калибровка и модель взгляда игрока, CSV сессий, дети клиники и их замеры. Всё это остаётся на телефоне.

## Как поставить на Supabase

1. Создать проект на supabase.com. Для тестов регион Frankfurt, до первых настоящих пользователей та же схема переезжает на свой сервер в Казахстане.
2. Открыть SQL Editor, вставить файл миграции целиком и нажать Run. Или из папки `backend`: `supabase link` и `supabase db push`.
3. Прислать в чат только Project URL и публичный ключ (anon, он же publishable). Ключ `service_role` не присылать никому и не класть в приложение или в репозиторий.

## Админ

Первый админ назначается один раз в SQL Editor, после того как он вошёл в приложение (или добавлен в Authentication → Users):

```sql
update public.accounts set role = 'admin'
where id = (select id from auth.users where email = 'почта админа');
```

Дальше премиум включается вручную в панели Supabase (Table Editor или SQL Editor), а когда появится своя админка, функцией `set_premium`. В обоих случаях изменение попадает в `admin_log`.

```sql
update public.accounts set premium_until = '2027-12-31' where id = 'id аккаунта';
```

## Проверка

```sh
backend/test/run.sh
```

Скрипт поднимает Postgres 16 в Docker, создаёт то, что Supabase даёт каждому проекту (роли, `auth.users`, `auth.uid()`), ставит миграцию и проверяет: чужие игроки и игры не видны и не меняются, старая запись не откатывает новую, открытый уровень не закрывается, игра не дублируется и не меняется, пользователь не может дать себе премиум или роль админа, каждое изменение премиума и роли пишется в журнал, удаление аккаунта уносит его игроков и игры.
